# Контрибьютинг
[English version](https://github.com/modoruru/create-modpack/blob/dev/CONTRIBUTING.md)
## Основное руководоство

### Не создавайте PR для форматирования или "очистки" кода
Если вы отправляете PR с изменениями в коде, можете исправить форматирование в области изменений, но, пожалуйста, не тратьте время всех на бессмысленные изменения.
Ни у кого нет времени рассматривать PR на изменение 1-2 строк.

### Не отправляйте изменений сделанных ИИ
Задавать вопросы ИИ и использовать эту информацию для написания кода - хорошо. Использовать ИИ для написания кода - Нет.
Вы будете заблокированы если будете отправять ИИ код в наши репозитории.

## Руководоство по стилю кода
- Используйте единственное число для пакетов, содержащих базовые интерфейсы или абстрактные классы. 
- Используйте множественное число только для пакетов, содержащих конкретные реализации.
- Избегайте использования префиксов `get`, `set` и `is` в названиях методов. Сигнатура метода и контекст должны ясно указывать на его назначение.
- Все классы, которые в будущем могут получить новые имплементентации желательно выносить в интерфейсы или абстрактные классы.
- Помечайте каждый класс как `final`, если он явно не предназначен для наследования.
- Всегда делайте утилитные классы `final` с `private` конструктором, чтобы предотвратить создание экземпляров.
- Не добавляйте внешние зависимости для функциональности, которая уже доступна в текущих зависимостях.
- Если блок кода не очень большой или не используется более чем в 1-2 местах, не следует выносить его в отдельный метод.

## Руководоство по Pull Request'ам
- Весь код содержащийся в PR должен следовать выше указанным требованиям, в противном случае мы попросим вас исправить это/откажем в merge'е.
- Если вы публикуете новый функционал, по необходимости напишите тесты, чтобы мы убедились в работе вашего изменения.

## Правила названий коммитов
Этот монорепозиторий содержит несколько проектов: `mod` и `modpack`. Для поддержания согласованности и наглядности истории коммитов **все коммиты должны соответствовать следующему правилу именования**:

```text
<тип изменений>(<область изменений>): <краткое описание изменений>
```

### Область изменений
Область (scope) определяет, на какой проект влияет коммит:

* `mod` - изменения, касающиеся самого мода
* `modpack` - изменения, касающиеся сборки, включая её конфигурацию и зависимости

### Тип изменений
Тип изменений который описывает назначение коммита:
* `wip` — работа в процессе (work in progress); используется для незавершенных изменений, которые еще не готовы к выпуску
* `chore` - изменения, связанные с сопровождением и не затрагивающие функциональность проекта, - например, обновление зависимостей, изменение конфигурации билда или инструментов
* `feat` - новая функция или функциональная возможность
* `fix` - исправление сломанного или неправильного поведения
* `test` - добавление или изменение тестов
* `ci` - CI/CD и изменения работы Github Actions

### Примеры
```text
feat(mod): add configurable teleport cooldown
chore(modpack): update dependencies
wip(mod): implement new networking system
```

Старайтесь делать описание **кратким, конкретным и сформулированным в повелительном наклонении** (там, где это возможно). Например, вместо `added support for X` (добавлена ​​поддержка X) лучше использовать `add support for X` (добавить поддержку X).
